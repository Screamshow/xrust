## 1. Главное

1. **Базовый путь Forkop X на rust-x работает.**
   - Проверены 18 конфигов из *настоящего* генератора Forkop (ucode собран из исходников): `check`, `run`, SIGHUP hot reload, `reload-plan`, `rule-set match`/`decompile`, формы Clash API, которые использует Forkop.
   - Через локальный xrust-сервер прошёл трафик VLESS REALITY/TLS + Vision, gRPC, XHTTP, WS и HTTPUpgrade.
   - Клиент совместим с серверами Xray и sing-box для TLS, REALITY, XHTTP (все режимы), gRPC, WS, H2 и Hysteria2. Исключения — FP-05 и FP-06.
2. **В ядре есть удалённо вызываемые крахи.**
   - Сборка использует `panic=abort` и `overflow-checks=false`, поэтому любая паника на данных из сети убивает весь процесс.
   - Подтверждено пять таких точек; одна из них доступна из LAN без аутентификации (CQ-01).
3. **Решения о доверии к сертификатам местами неверны.**
   - REALITY при неудачной аутентификации откатывается на обычную проверку цепочки (SEC-01).
   - `insecure` молча отключает pins (SEC-02). Forkop генерирует оба этих случая.
   - Плюс две уязвимые зависимости TLS (BLD-01, BLD-02).
4. **В путях Forkop по умолчанию есть утечки ресурсов, которые доводят до OOM.**
   - XHTTP packet-up (`mode: auto`) не закрывает сессии: за 6 минут RSS вырос с 37 до 229 МБ (CN-02 = MEM-01).
   - XHTTP-пул не обнаруживает мёртвое соединение (CN-01).
   - UDP NAT держит 64 КиБ на поток без лимита (MEM-02).
5. **Два блокера совместимости с Forkop.**
   - Один узел trojan, ss, vmess или socks в подписке валит весь конфиг (FX-01).
   - ByeDPI не работает на rust-x (FX-02).
6. **Отпечатки.**
   - ECH GREASE в профилях chrome и firefox — статичные байты, общие для всех установок (FP-01).
   - JA4 совпадает с Xray и sing-box, но JA3 у chrome постоянен (FP-02).
   - Hysteria2 даёт отпечаток rustls/quinn вместо quic-go (FP-04).
7. **Сильные стороны.**
   - REALITY+Vision: 1,7 с CPU/ГиБ против 2,1 у sing-box и 2,4 у Xray; RSS 29 МБ против 60 и 37.
   - Простой на musl: 4,4 МиБ (пустой конфиг), 8,2 МиБ (urltest на 50 узлов).
   - На musl память после спада нагрузки возвращается полностью.
   - Утечек задач и fd при 30 in-place и 10 полных reload нет.
   - fastgcm и fastchacha совпали с эталоном на 21 780 векторах.
   - Проверка цепочки, имени и срока сертификата корректна в обоих TLS-стеках.
   - Даунгрейда на TLS 1.2 нет.

### Что я перепроверил лично (поверх отчётов по разделам)
- **SEC-01.** Подтверждено. `core-tls/src/verify.rs:395`: при несовпадении HMAC вызывается `self.fallback.verify_chain(...)`. При `insecure` fallback — это `AcceptsAnything` (`core-runtime/src/tls_client.rs:667`).
- **SEC-04.** Подтверждено. `core-runtime/src/http_client.rs:367-381`: размер чанка из сети идёт в `start + size + 2` без checked-арифметики, при `overflow-checks=false` сумма переполняется и срез паникует.
- **FP-01.** Подтверждено. `core-tls/src/fingerprints.rs`: расширение `0xfe0d` задано как `Ext::Static` с фиксированными байтами в 7 шаблонах.
- **CN-02.** Механизм подтверждён. `outbound/transport/xhttp.rs:1579`: `poll_shutdown` закрывает только upload-половину.

## 2. Измеримые результаты

### 2.1 Память
Замеры на x86_64; ближайший аналог роутера — musl со своим malloc. Подробности в отчёте 04.

| Сценарий | RSS |
|---|---|
| Пустой конфиг, простой | 4,4 МиБ (anon 0,5) |
| urltest на 50 узлов, простой | 8,2 МиБ |
| Forkop-подобный конфиг + rule sets ~430 тыс. записей | 41 МиБ steady, **пик старта 71–77 МиБ** |
| 1000 соединений direct (splice) | ~11 КиБ на соединение |
| 1000 соединений VLESS+TLS: простой / передача | 24 / 100–120 КиБ на соединение |
| 1000 соединений gRPC | 200–250 КиБ на соединение, пик 237 МиБ |
| 1000 соединений XHTTP | 380–550 КиБ на соединение, **пик 669 МиБ** (mimalloc 1,06 ГиБ) |
| UDP-поток | 12–78 КиБ, без лимита потоков |
| 12 минут со сменой соединений | плато anon 110–120 МиБ на musl, ~380 МиБ на mimalloc; рост ~1,4 МиБ/мин |
| `rule-set match` рядом с живым ядром | пик 43–60 МиБ |

**Вывод для роутеров:**
- На 128 МБ с rule sets размера HaGeZi не помещается уже пик старта, особенно вместе с `rule-set match` или `check` от Forkop.
- На 256 МБ сотни соединений через XHTTP или gRPC приводят к OOM.

### P1

**Безопасность**
- SEC-06: Clash API на LAN без secret, CORS `*`, без проверки Host. Это отчасти конфигурация Forkop.
- SEC-07: http_client держит тело любого размера при большом Content-Length.
- SEC-08 = CQ-11: DNS не сверяет ID и question ответа, ID последовательный.
- SEC-09: VLESS encryption 0-RTT — повтор nonce.
- SEC-10 = CQ-05: Hysteria2-сервер, неограниченный padding ведёт к abort.
- SEC-11: REALITY-сервер без fallback.
- BLD-03: `rustls 0.23.45`.
- BLD-04: в CI нет cargo audit/deny.

**Стабильность и ресурсы**
- CQ-04: TSRS mmap с невыровненным `&[Ipv6Entry]`, это UB.
- CQ-08: дефрагментатор HY2 без TTL.
- CQ-09 = CN-15: TUN, полуоткрытые сессии не удаляются.
- CQ-10: DNS hijack без лимита.
- CQ-12: бесконечная рекурсия bbolt на повреждённом cache.db, это crash-loop.
- CQ-13 = MEM-08: cache.db переписывается целиком, синхронно, без fsync; весь лежит в heap.
- CQ-14: WireGuard с `listen_port` ломает in-place reload, а с ним DNS failover Forkop.
- CQ-15 / CN-31: WireGuard без защиты от повтора handshake.
- CQ-16 = BLD-05: fd TUN не закрывается.
- CQ-17: 1,56 мс на соединение при 5000 доменов.
- CQ-18: NTP с именем хоста блокирует старт.
- MEM-07: SRS грузится через JSON `Value`, пик ×2–3.
- MEM-05: mimalloc на x86_64 не отдаёт память.

**Соединения**
- CN-04 = FP-12: XHTTP `auto` вместо stream-one выбирает packet-up даже с REALITY.
- CN-05 = FP-13: последовательные POST в packet-up.
- CN-06 = MEM-13 = CQ-26: нет idle-таймаута, keepalive и дедлайна handshake.

- CN-26: H2MUX-клиент не переживает смерть сессии.
- MEM-04: XHTTP-буфер 1 МБ на сессию.

- FP-04: HY2 на rustls/quinn, без MLKEM.

## 4. План исправлений

Главное правило: **каждое изменение проходит контрактные тесты Forkop X** (этап 0) до и после. Правки на стороне Forkop (FX-01, FX-02, SEC-02, SEC-06) согласуются отдельно — это другой репозиторий.

### Этап 0 — страховочная сетка (до любых правок, 1–2 дня)
1. Перенести в xrust CI фикстуры c01–c16, полученные из генератора Forkop (`$S/forkop/configs/`), и прогонять `check` и `run` на loopback. Это пункты 1–12 из §9 отчёта 07: контракт `version`, CLI, Clash API, hot reload, SIGTERM, DNS.
2. Добавить в CI:
   - тесты профиля rust-x (BLD-12);
   - `cargo audit` с учётом вендоренных крейтов (BLD-04);
   - clippy по профилю rust-x.
3. Добавить фазз-цели или property-тесты для SRS, DNS-кодека, SOCKS, http_client chunked и Clash API path. Это регрессии для P0 №1–5.

### Этап 1 — P0 безопасности и крахов (минимальные, точечные правки)
- №1–3, 5: checked-арифметика и проверка границ в парсерах; лимиты zlib/zstd и размеров; `percent_decode` по байтам. Риск низкий, поведение для валидных данных не меняется.
- №4 (SEC-05): rule-set и external_ui через проверяющий TLS-клиент. Риск: узлы с самоподписанными зеркалами rule-set сломаются; нужна явная опция и проверка того, что Forkop не использует такие источники.
- №6 (SEC-01): при провале аутентификации REALITY — всегда ошибка, независимо от `insecure`, как в Xray.
- №7 (SEC-02): pins работают и при `insecure`, то есть pin заменяет chain-check, но не отключается. На стороне Forkop не передавать `allowInsecure` молча.
- №8 (SEC-03): проверять CertificateVerify в MASQUE PinVerifier.
- №9, 10: `cargo update -p rustls-webpki -p webpki-roots -p rustls` (semver-совместимо) и `ruzstd` ≥ 0.9.1 (правка `Cargo.toml`). Это требует отдельного разрешения: в рамках аудита обновления не делались, сборкой не проверено.

### Этап 2 — P0 ресурсов и соединений
- №11 (CN-02): закрытие download-половины packet-up и отмена сессии при shutdown; таймер после half-close в relay (заодно CN-06).
- №12 (CN-01, затем CN-07 и CN-08): H2 PING keepalive и проверка живости в H2Pool, удаление мёртвых соединений, учёт GOAWAY. Только после этого — пул для gRPC.
- №13 (MEM-02 и CQ-06): лимит числа UDP-потоков, буфер по фактическому размеру датаграммы вместо 64 КиБ, очередь пакетов на время открытия потока вместо задачи на пакет.
- №14 (CN-03): `server_ports` без `server_port` и утечка при hopping.
- Критерий приёмки: долгий прогон из отчёта 04 (12 минут со сменой соединений, 1000 соединений XHTTP и UDP) на musl-сборке. Цели:
  - нет CLOSE_WAIT старше таймаута;
  - плато anon не больше 60 МиБ;
  - throughput REALITY и XHTTP не хуже текущего более чем на 3 %.

### Этап 3 — совместимость с Forkop и отпечатки P0
- FX-01, FX-02: **решение за вами.**
  - Вариант (а): Forkop фильтрует неподдерживаемые узлы для rust-x с WARN.
  - Вариант (б): rust-x отклоняет только сам узел, а не весь конфиг.
  - Вариант (в): вернуть `socks` outbound в профиль rust-x, это нужно для ByeDPI.
  - Рекомендация: (а) + (в). `socks` нужен ByeDPI и стоит мало.
- FP-01: генерировать ECH GREASE на каждое соединение (случайные config_id, enc, payload нужной длины), как Chrome. Крипто не затрагивается.
- FP-06: base64url без паддинга и поддержка `early_data_header_name`; интероп-тест с sing-box и Xray.
- FX-03, FX-04 (P1): принять `panic` как алиас; отдавать capabilities из самого бинарника.

## 5. Технический долг
- **Тестовое покрытие.** 1493 теста проходят, но:
  - профиль rust-x в CI не тестируется (локально 139 падений, почти все — legacy-тесты);
  - нет фаззинга сетевых парсеров;
  - нет тестов на конфигах Forkop;
  - aarch64 не исполняется;
  - toolchain не закреплён.
- **`panic=abort` + `overflow-checks=false`.** Эту пару стоит оставить ради размера и скорости, но тогда каждый парсер обязан использовать checked-арифметику. Альтернатива — включить `overflow-checks` выборочно, но такого per-crate флага для кода нет, только через профиль.
- **Вендоренный h2.** Три изменения вместо одного документированного, отставание от 0.4.20, cargo audit его не видит.
- **Собственный TLS-стек.** Дорог в сопровождении: мелкие отклонения от RFC (SEC-24) и ручные шаблоны отпечатков, которые устаревают (FP-19).
- **Документация расходится с кодом:** README.en, CHANGELOG, `docs/SIZING.md`, `openwrt/Makefile` (FX-16), поле `repository` в `Cargo.toml`.
- **Воспроизводимость сборки:** в бинарнике 397 путей `/home/<user>/.cargo`, нужен `--remap-path-prefix` (BLD-13).

## 6. Ограничения аудита
- **Нет root, netns, tc/netem, tcpdump, perf, qemu и устройства.** Поэтому:
  - TProxy, TUN, `routing_mark`, nft, watchdog и установка IPK/APK проверены только по коду;
  - сеть эмулировалась userspace-прокси;
  - TCP-опции на проводе не видны.
- **Память и CPU мерились на x86_64** (musl и gnu), а не на aarch64/Cortex-A53. Хост во время замеров был нагружен (load 30–40). Цифры относительные.
- **x86_64-musl штатно не собирается** без `musl-gcc` (mimalloc). Для замеров сделана копия дерева без mimalloc в scratchpad.
- **JA4 не сверялся** с опубликованными значениями браузеров: внешние запросы запрещены.
- **Обновления зависимостей** (BLD-01…03) не проверены сборкой.
- **Отклонения от ограничений** (раскрываю):
  - Один прогон URLTest при проверке совместимости открыл 8 соединений к `www.gstatic.com:443` — внешний хост, не прокси-узел и не роутер. После этого egress ограничен loopback (отчёт 07, §2.4).
  - До запрета внешних подключений сборочная проверка скачала advisory-db, `.crate` h2 и blake3 и инструменты. Проверка отпечатков скачала Xray и sing-box (официальные релизы) и использовал crates.io API. После запрета все работали офлайн.
  - Попытка `cargo update` в *копии* репозитория в scratchpad была заблокирована классификатором прав. Репозиторий не затронут.
