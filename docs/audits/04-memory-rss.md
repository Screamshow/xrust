# Аудит 04: RAM/RSS на роутерах OpenWrt 128/256 МБ

- Объект: xrust v0.0.26 (`c5f567c`), сборка `-p core-cli --no-default-features --features rust-x --release` (`--locked`).
- Дата: 2026-10-23.
- Исходный код репозиториев не менялся. Все прогоны шли только на loopback (порты 22001–22243), внешних подключений не было. URLTest пробует `http://127.0.0.1:22005/generate_204`, удалённые rule set скачиваются с локального HTTP.
- Обозначения статуса:
  - **[подтверждено]** — есть команда и цифры;
  - **[статически]** — вывод по коду без замера;
  - **[гипотеза]** — вывод не проверен.

## 0. Главное

1. **На x86_64 измерены три сборки**, ни одна не равна роутерной aarch64/musl:
   - `musl`: x86_64-unknown-linux-musl, статическая, системный mallocng musl. Это ближайший аналог aarch64/musl по поведению аллокатора. Отличаются ISA, размер страниц, работа crypto и кэши CPU.
   - `mimalloc`: штатная gnu-сборка. Mimalloc линкуется только на x86_64.
   - `glibc`: gnu без mimalloc.
2. **Простой** (2 worker'а):
   - пустой конфиг: 4,4 МиБ RSS / 0,5 МиБ anon (musl);
   - конфиг в стиле Forkop с крупными rule set (~430 тыс. записей): **41 МиБ RSS, 34 МиБ anon, пик при старте VmHWM 71 МиБ**.
3. **Стоимость соединения** (musl, ΔRssAnon/N при 1000 одновременных соединений):

   | Цепочка | КиБ на соединение |
   |---|---:|
   | direct (splice) | ≈11 |
   | VLESS+TLS, простаивающее | ≈24 |
   | VLESS+TLS, с передачей | ≈100–120 |
   | VLESS+gRPC | ≈200–250 |
   | VLESS+XHTTP (packet-up) | ≈380–550, и память не освобождается |
   | UDP-поток | 12–64 (зависит от аллокатора и «возраста» кучи) |

4. **Найдено, P0:**
   - **MEM-01.** XHTTP-сессии не закрываются после FIN клиента: 100 % сокетов остаются в CLOSE_WAIT, память и fd не возвращаются ≥ 6 мин.
   - **MEM-02.** UDP NAT держит 64 КиБ на поток, лимита потоков нет. В 12-минутном тесте с перемешиванием соединений живая куча доходила до 335 МиБ: musl RSS ≈ 120 МиБ, mimalloc RSS ≈ 384 МиБ.
5. **Найдено, P1:**
   - **MEM-03.** gRPC: отдельное h2-соединение на каждое проксируемое соединение плюс 384 КиБ буферов vendor-h2.
   - **MEM-04.** XHTTP: буфер 1 000 000 Б на сессию.
   - **MEM-05.** mimalloc на x86_64 почти не возвращает память ОС: после спада удерживает 96–323 МиБ.
   - **MEM-07.** Rule sets: временный пик ×2–3 при загрузке.
   - **MEM-08.** cache.db целиком в heap.

## 1. Методология

### 1.1 Сборки

Корень scratchpad: `S=<scratch>`.

```bash
source ~/.cargo/env
# A. штатная gnu + mimalloc (оригинальное дерево)
CARGO_TARGET_DIR=$S/target-mem cargo build --locked -p core-cli --no-default-features --features rust-x --release
# B. копия дерева $S/src-nomi (Cargo.toml, Cargo.lock, crates, vendor, tools, lx-specs, .cargo):
#    в crates/core-cli/src/main.rs и Cargo.toml cfg `target_arch = "x86_64"` заменён на
#    `target_arch = "x86_64_nomimalloc_audit"` (mimalloc выключен),
#    в allocstat.rs mimalloc::MiMalloc -> std::alloc::System, путь дампа берётся из TACHYON_ALLOCSTAT.
#    Скрипт: $S/mem/build-variants.sh
CC_x86_64_unknown_linux_musl=gcc cargo build --locked ... --target x86_64-unknown-linux-musl   # bin/musl
cargo build --locked ... --target x86_64-unknown-linux-gnu                                     # bin/glibc
cargo build --locked ... --features rust-x,allocstat --target x86_64-unknown-linux-musl        # bin/musl-as
```

Про musl-сборку:
- Она получилась без musl-gcc: rust-lld и self-contained CRT уже настроены в `.cargo/config.toml`.
- C-код есть только у `blake3` (vendored), его собрал gcc.
- `libmimalloc-sys` исключён cfg.
- Бинарники лежат в `$S/mem/bin/{mimalloc,glibc,musl,musl-as}`.

Условия прогонов:
- `TACHYON_WORKERS=2` (типичный 2-ядерный роутер).
- Для mimalloc задан `MIMALLOC_ALLOW_THP=0`, иначе цифры искажает THP (MEM-06).
- Хост: 28 ядер, THP=madvise, процесс не root.
  - Поэтому `F_SETPIPE_SZ` упирается в `pipe-user-pages-soft` (16384 страниц на uid, общий с другими аудиторами).
  - На роутере (root) размер pipe не ограничен.

**allocstat.** Включается фичей `allocstat`, вывод — по строке в секунду при заданном `TACHYON_ALLOCSTAT`:
- `live` — живая куча;
- `peak`;
- `cls=<класс>:<объектов>x<КиБ>`;
- `big=<точный размер>:<n>x<КиБ>` — для объектов ≥ 64 КиБ.

В оригинале allocstat оборачивает mimalloc и пишет в фиксированный `/tmp/tachyon-allocstat.txt` (MEM-16). Для аудита использована копия с `System` (musl) и путём из переменной.

### 1.3 Конфиги (по мотивам `forkop/files/usr/lib/singbox/generator.uc`)

`forkop.json` содержит:
- inbound `mixed` вместо `tproxy` (tproxy требует root) и `direct` `dns-in`;
- DNS: udp `dns-server` и `bootstrap`, `fakeip` 198.18.0.0/15 + fc00::/18, `strategy prefer_ipv4`;
- правила `predefined HTTPS`, `reject use-application-dns.net`, `rule_set → fakeip-server rewrite_ttl 60`;
- route: `hijack-dns`, `sniff`, `rule_set → main-out`, `final direct-out`;
- 50 VLESS+TLS узлов → `urltest` (interval 3m, tolerance 50) → `selector`;
- rule sets: 6 local binary и 3 remote binary (`update_interval 1d`) с локального HTTP;
- `cache_file` с `store_fakeip`, `clash_api` на 127.0.0.1:22009.

Варианты: `forkop-norules-nonodes`, `urltest50` (без rule set), `forkop-rules-only`, `forkop-mmap` (`mmap:true, mode:mmap`).

### 2.4 UDP NAT

[подтверждено]

- **1000 потоков через `direct` inbound** (`suite1`):

  | Аллокатор | ΔRSS при удержании | На поток | Вернулась ли память через 70 с |
  |---|---:|---:|---|
  | musl | +12,4 МиБ | 12,4 КиБ | нет (fd 903) |
  | mimalloc | +16,8 МиБ | 16,8 КиБ | нет |
  | glibc | +34,5 МиБ | 34,5 КиБ | нет |

  Через 70 с память не вернулась ни у одного аллокатора, потому что тайм-аут потока 120 с, а очистка идёт раз в 30 с.
- **В полном Forkop-конфиге** (`suite2`) на 1000 потоков: musl +11,7 МиБ, **mimalloc +45 МиБ (≈52 КиБ на поток)**, glibc +19,6 МиБ.
- **Живая куча — 64 КиБ на поток при любом аллокаторе.** Разница в RSS объясняется тем, сколько страниц буфера реально тронуто. musl/mallocng не обнуляет свежие mmap-группы. mimalloc обнуляет.
- **DNS через `dns-in` (hijack) потоков не создаёт.** 3000 запросов с разных портов дали +0,8 МиБ (`dnsports.py`).
- Потери ответов в `udpload` (1–2 тыс. из 3 тыс.) — ограничение однопоточного Python-клиента, а не xrust [гипотеза].

- Прогон allocstat (`longrun_as.py`) показал:
  - **живая куча на плато 330–350 МиБ, из них 4 799 буферов по 65 536 Б = 307 МиБ** (UDP-потоки за последние ≈150 с);
  - после спада — 32,5 МиБ против 22,4 МиБ на старте (+10 МиБ: DNS LRU, FakeIP, cache.db).

- **mimalloc** на x86_64 **после спада удерживает 323 МиБ** (MEM-05).
- Во время mimalloc-прогона параллельный `longrun_as.py` удалил его `run/cache-forkop.json.db`. На цифры памяти это не влияет: зеркало в heap осталось.

### 2.6 Медленный потребитель (kernel-память)

[подтверждено] `slowtest.sh 20`; sink не читает.

- 20 соединений, клиент протолкнул 221 МиБ.
- xrust: RSS 6,4 МиБ, но **`memory.stat sock` = 145,6 МиБ, т. е. ≈7,1 МиБ на соединение**.
- Это сокетные буферы TCP (автонастройка до `tcp_rmem` 6 МиБ / `tcp_wmem` 4 МиБ) плюс содержимое pipe.
- Общее свойство любого прокси с двумя сокетами. Специфичны для xrust только pipe по 1 МиБ (MEM-12).
- На роутере сверху ограничивает `tcp_mem` [гипотеза: на 128 МБ давление начинается при единицах МиБ].

## 4. Tokio и потоки

[подтверждено/статически] `crates/core-cli/src/main.rs:213-236`.

- **worker_threads** = `TACHYON_WORKERS` или `available_parallelism()` (учитывает affinity).
  - На роутере с 1–4 ядрами получается 1–4 worker'а.
  - При 1 ядре используется `new_current_thread`.
  - Измерено: потоков = workers + 1.
- **max_blocking_threads**: 16 при w=1, `16*workers` иначе. Потоки создаются по требованию и уходят через 10 с простоя (`thread_keep_alive` по умолчанию). При старте forkop наблюдалось до 11 blocking-потоков.
- **thread_stack_size** не задан: 2 МиБ виртуально. RSS — только тронутые страницы (единицы–десятки КиБ).
- `event_interval(31)`.
- Таймеры: глобальное колесо tokio; на UDP-поток перевзводимый timeout и sweeper раз в 30 с.
- Вывод: tokio-конфигурация дешёвая, менять не нужно (P3). Если урезать blocking-пул (`max_blocking_threads(4)`), выигрыш — до ≈100 КиБ RSS стеков при всплесках; риск — блокировки DNS/netns при всплеске.

## 5. Находки

Поля каждой находки: статус, приоритет, место, причина, последствия, исправление, выигрыш, риск, влияние на Forkop X.

### MEM-01. XHTTP: сессии не завершаются после закрытия клиентом — P0

- **Статус:** [подтверждено] `xhttp_leak.sh musl`, `run/xhttp-leak-musl.out`.
  - 100 соединений mixed → VLESS+TLS+XHTTP (mode по умолчанию `auto` → packet-up, `xhttp.rs:819`).
  - После закрытия клиентом: **100 из 100 сокетов inbound :22042 в CLOSE_WAIT**.
  - Клиент держит fd 116 и anon 15,2 МиБ, сервер — fd 116 и 20 МиБ.
  - Через 30/60/120/240/360 с без изменений.
  - На 1000 соединений после спада осталось 410 МиБ (musl) и 404 МиБ (mimalloc), fd 1626 (`results3.jsonl`).
  - VLESS+TLS и gRPC в тех же условиях закрываются (fd возвращаются к 13).
- **Место:** `crates/core-runtime/src/outbound/transport/xhttp.rs`.
  - Upload: `packet_upload_worker`, `:1613-1660`, на EOF делает `break`.
  - Download: `SplitConn`, `:1600-1611`, — снимается только Drop'ом.
- **Причина** [гипотеза]:
  - В packet-up EOF uplink'а никак не сигнализируется серверу.
  - Клиент продолжает ждать download-GET, сервер ждёт данных от upstream.
  - Upstream (echo, или реальный HTTP keep-alive) не получает FIN и не закрывается.
  - Idle-таймаута на relay нет (см. MEM-13).
  - С сервером Xray удержание, вероятно, ограничено его `connIdle` ≈300 с [не проверено].
- **Последствия:**
  - Неограниченный рост RSS и fd в реальном использовании: браузер закрывает keep-alive соединения со своей стороны.
  - ≈150–400 КиБ на каждое закрытое соединение. OOM за минуты–часы.
- **Исправление:**
  - При EOF uplink'а и закрытии inbound-стороны: обрывать download-GET (drop h2-стрима, RST_STREAM) и завершать сессию, как это делает Xray при отмене запроса.
  - Добавить idle-тайм-аут сессии.
  - Покрыть тестом: закрыть клиент → проверить, что `SplitConn` дропнут, а fd сервера закрыт.
- **Выигрыш:** вся удерживаемая память, ≈0,15–0,4 МиБ на закрытое соединение. На 1000 — 400 МиБ.
- **Риск для throughput:** нет.
- **Forkop X:** узлы из подписок с `type: xhttp` (REALITY+XHTTP проверяется в `tests/reality_xhttp*.sh`) неизбежно приведут к OOM. До исправления — P0 для релиза с XHTTP.

### MEM-02. UDP NAT: 64 КиБ на поток, без лимита потоков — P0

- **Статус:**
  - [подтверждено] allocstat: 738×65 536 Б на 1000 потоков; в долгом тесте 4 799×65 536 Б = 307 МиБ живой кучи.
  - RSS: musl 12 КиБ на поток при свежей куче, до ≈60 КиБ при обороте; mimalloc ≈52 КиБ.
  - Долгий тест: плато musl ≈110–120 МиБ, mimalloc ≈380 МиБ.
  - [статически] Дополнительные буферы на проксируемый UDP: `outbound/packet.rs:327` (64 КиБ), UoT `uot.rs:82,97` (2×64 КиБ), mixed UDP ASSOCIATE `mixed.rs:469`.
- **Место:**
  - `crates/core-runtime/src/inbound/udp.rs:877` — `vec![0u8; 64 * 1024]` в обратной задаче каждого потока;
  - `:334` — HashMap потоков без ограничения;
  - `:25` — `DEFAULT_UDP_TIMEOUT` 120 с;
  - `:26` — sweep раз в 30 с.
- **Причина:** буфер приёма на весь срок жизни потока плюс отсутствие лимита потоков.
- **Последствия:**
  - Торрент/DHT, игры, WebRTC, Discord voice, STUN дают тысячи потоков за 150 с: 64–200+ МиБ.
  - OOM на 128/256 МБ.
  - QUIC в Forkop по умолчанию reject'ится (`disable_quic`), DNS идёт через hijack и потоков не создаёт [подтверждено]. Но с `disable_quic=0` QUIC тоже станет UDP-потоками.
- **Исправление:**
  1. Читать через `readable()` + `try_recv` в общий буфер воркера (или в 2 КиБ стековый с fallback на 64 КиБ для крупных датаграмм) и копировать n байт.
  2. Лимит потоков (LRU, например 4096 или по MemTotal).
  3. Укоротить тайм-аут для не-DNS потоков без ответа (sing-box: 5 мин по умолчанию — здесь уже меньше; можно 60 с для потоков без ответа).
- **Выигрыш:** ≈52–62 КиБ на поток; на 2000 потоков 100–120 МиБ.
- **Риск:** лишний memcpy датаграммы ≤1,5 КиБ — пренебрежимо.
- **Forkop X:** tproxy UDP всех LAN-клиентов идёт сюда. Это главный источник OOM на роутерах с торрент-клиентами.

### MEM-03. gRPC: h2-соединение и 384 КиБ буферов на каждое проксируемое соединение — P1

- **Статус:**
  - [подтверждено] allocstat: на соединение 262 144 + 131 072 + 65 536 Б; 474 КиБ живой кучи в простое.
  - RSS musl: 202–247 КиБ на соединение, на 1000 соединений VmHWM 237 МиБ; mimalloc 375 МиБ.
  - [статически] `outbound/transport/grpc.rs:65-72` — `handshake` на каждый `connect`.
- **Место:**
  - `vendor/h2/src/codec/mod.rs:52` — `FramedRead` 256 КиБ, в upstream 8 КиБ;
  - `vendor/h2/src/codec/framed_write.rs:64` — `DEFAULT_BUFFER_CAPACITY` 128 КиБ, в upstream 16 КиБ;
  - `outbound/transport/h2io.rs:22-25` — окна 8/32 МиБ, `MAX_FRAME` 256 КиБ.
- **Причина:** буферы под 10+ Гбит/с на loopback-бенчмарках выделяются сразу при создании соединения, плюс нет мультиплексирования.
- **Последствия:**
  - 200+ МиБ на 1000 соединений.
  - Медленный читатель может забуферизовать до 8 МиБ на поток [статически].
- **Исправление:**
  1. Начальная ёмкость `FramedRead` 16–32 КиБ и `FramedWrite` 16 КиБ, рост по требованию (у `BytesMut` он уже есть).
  2. На устройствах с MemTotal < 512 МБ — окна 2–4 / 8 МиБ (настраиваемо).
  3. Опционально — мультиплексировать gRPC-потоки поверх одного h2 к серверу (как xmux).
- **Выигрыш:**
  - ≈330 КиБ виртуально и ≈100–200 КиБ RSS на соединение, на 1000 — 100–200 МиБ;
  - мультиплексирование — ещё ≈20–40 КиБ (TLS, сокет) на соединение.
- **Риск:**
  - Рост буфера на первом крупном кадре — пара realloc, это незаметно.
  - Окно 2 МиБ при RTT 50 мс ограничивает один поток до ≈320 Мбит/с. Для WAN роутера это допустимо, для loopback-бенчмарка нет, поэтому лимит должен зависеть от MemTotal.
  - Мультиплексирование даёт HOL-блокировку: только opt-in.
- **Forkop X:** grpc-узлы из подписок. На 256 МБ при нескольких сотнях соединений будет OOM.

### MEM-04. XHTTP packet-up: буфер 1 000 000 Б на сессию — P1

- **Статус:**
  - [подтверждено] allocstat: 200×1 000 000 Б, 1,15 МиБ живой кучи на сессию.
  - RSS musl 380–546 КиБ, mimalloc 975 КиБ на соединение; при 1000 соединений VmHWM 669 МиБ / 1,06 ГиБ.
- **Место:** `outbound/transport/xhttp.rs:211-212` (значение по умолчанию `sc_max_each_post` 1 000 000), `:1620-1622` (`vec![0u8; max_each]`), плюс duplex 128 КиБ (`:660,967`).
- **Причина:** под пакет выделяется максимальный размер, а не фактический.
- **Последствия:** вместе с MEM-01 — быстрый OOM. Без MEM-01 — ≈0,5 МиБ на активное соединение.
- **Исправление:**

- **Риск:** при крупных POST пара realloc. Окно батчинга 30 мс не меняется.
- **Forkop X:** `generator.uc:1926` задаёт `sc_min_posts_interval_ms = 30` и `sc_max_each_post` не трогает, то есть берётся 1 МБ по умолчанию.

### MEM-05. mimalloc (x86_64) почти не возвращает память после спада — P1 для x86_64-роутеров

- **Статус:** [подтверждено] с `MIMALLOC_ALLOW_THP=0` (заданный в коде `purge_delay=0` действует).

  | Сценарий | Что удержано после спада |
  |---|---|
  | TLS ×1000 | 96 МиБ из 99 (сервер 128 из 144) |
  | gRPC ×1000 | 164 МиБ |
  | direct ×1000 | 9,4 МиБ |
  | долгий тест | 323 из 384 МиБ |

  musl в тех же сценариях возвращает всё. glibc тоже удерживает: 77 МиБ после TLS; rule sets — 81 МиБ steady против 33 у musl.
- **Место:**
  - `crates/core-cli/src/main.rs:3-10` — `#[global_allocator]` на x86_64;
  - `:600-605` — `mi_option_set`;
  - `Cargo.toml` core-cli — `mimalloc` для `target_arch = "x86_64"` (в том числе x86_64-musl).
- **Причина** [гипотеза]: страницы, освобождённые из чужого потока, и брошенные сегменты mimalloc v3 не очищаются без аллокаций в потоке-владельце. `purge_delay` действует только на уже свободные страницы.
- **Последствия:** на x86_64 OpenWrt (виртуальные машины Forkop на 256 МиБ, x86-роутеры) после пика RSS не опускается. Пики накапливаются вплоть до OOM.
- **Исправление:** одно из двух —
  - периодический `mi_collect(true)` (например, раз в 5–10 с при падении числа соединений) и `MIMALLOC_ARENA_EAGER_COMMIT=0` / `MIMALLOC_PURGE_DECOMMITS=1`;
  - решение «на роутерах системный malloc» и для x86_64-musl, как на aarch64.
  
  Перед выбором замерить пропускную способность.
- **Выигрыш:** 10–320 МиБ RSS после спадов.
- **Риск:** `mi_collect` стоит CPU (миллисекунды на сотни МиБ). musl malloc медленнее на мелких аллокациях; отдельный аудит пропускной способности отмечает влияние на h2/TLS [не проверено здесь].
- **Forkop X:** x86_64-пакет `rust-x`. На aarch64 не проявляется: там mimalloc нет.

### MEM-06. `mi_option_set(43 /*allow_thp*/, 0)` не действует — P2

На хостах с THP это P1.

- **Статус:** [подтверждено] Хост с THP=madvise, конфиг direct, 2 worker'а:

- **Исправление:**
  - не держать bucket `rule_set` в памяти: читать лениво или не хранить, если есть TSRS/файл;
  - инкрементальная запись или хотя бы сериализация без клонирования;
  - убрать немедленный flush в `save_to_cache`.
- **Выигрыш:** 1× размер remote-наборов постоянно (единицы–десятки МиБ на реальных geosite), плюс 2–3× db на пиках flush.
- **Риск:** нет.
- **Forkop X:** `cache_file.enabled=true, store_fakeip=true` всегда (`generator.uc:525-528`), community-наборы remote — именно тот случай.

### MEM-09. Режим mmap: TSRS в `/tmp` (tmpfs = RAM), пересборка на каждом старте — P2

- **Статус:** [подтверждено]
  - steady anon 2,2 МиБ против 33;
  - но VmHWM 77 МиБ (больше, чем в heap-режиме);
  - TSRS 11,9 МБ против 5,3 МБ SRS (×2,2), записаны в `/tmp/tachyon-rulesets/` (после теста удалены).
- **Место:**
  - `route/rule_set_remote.rs:45-53` — `default_tsrs_cache_path` в `/tmp`;
  - `route/mod.rs:508-531, 556-578` — compile → write → open при каждом старте для local SRS.
- **Причина:** TSRS не кэшируется по хэшу источника; путь на tmpfs.
- **Последствия:**
  - на OpenWrt страницы tmpfs — это неосвобождаемая RAM (без swap): экономия ≈31 МиБ heap превращается в ≈12 МиБ shmem;
  - пик при старте не уменьшается.
- **Исправление:**
  - путь TSRS настраиваемый (overlay или флеш) или рядом с SRS;
  - пропускать пересборку при совпадении sha;
  - компилировать без `Value` (см. MEM-07).
- **Выигрыш:** ≈20 МиБ steady и ≈40–60 МиБ пика.
- **Риск:** износ флеша при частых обновлениях: писать только при изменении.
- **Forkop X:** Forkop не задаёт `mmap`/`mode` (поля не из sing-box), значит работает heap-режим. Включать mmap имеет смысл только после исправления.

### MEM-10. `rule-set match` для валидации: 60 МиБ пика на 300 тыс. доменов — P2

- **Статус:** [подтверждено] таблица в §2.7.
- **Место:** `crates/core-cli/src/rule_set.rs:344` (`cmd_rule_set_match`, тот же путь SRS → `Value` → индекс).
- **Последствия:** Forkop запускает его при обновлении списков, пока резидентное ядро держит 34–41 МиБ. Это прямой повтор сценария OOM из `docs/oom-ruleset-validation.md`.
- **Исправление:**
  - режим `--validate`: потоковый разбор без построения индекса;
  - или проверять формат и считать записи.
- **Выигрыш:** ≈55 МиБ пика.
- **Риск:** нет.
- **Forkop X:** `ruleset_cache.uc` и `list_cache` (валидация binary).

### MEM-11. TLS: 64 КиБ (+8 КиБ) живой кучи на простаивающее соединение; relay 2×128 КиБ при передаче — P2

- **Статус:** [подтверждено]
  - allocstat: 500×65 536 + 504×8 КиБ; RSS 24 КиБ, потому что страницы не тронуты;
  - при передаче ≈100–120 КиБ RSS на соединение.
- **Место:**
  - `inbound/mod.rs:678-688` — `relay_buf()` = 2×65 535, `TACHYON_RELAY_BUF`;
  - `:695-710` — пул на 16 буферов;
  - источник 64 КиБ в простое точно не локализован. Кандидаты: `tls_utls.rs:21` `CHUNK` (по коду освобождается после опустошения) и буфер приёма rustls.
- **Последствия:** при сотнях активных загрузок — 100+ МиБ. На musl после завершения память возвращается.
- **Исправление:**
  - на MemTotal < 512 МБ по умолчанию `TACHYON_RELAY_BUF` 32–64 КиБ;
  - найти и освобождать 64 КиБ буфер простаивающего соединения.
- **Выигрыш:**
  - 64–192 КиБ на активное соединение;
  - до 64 КиБ виртуально и ≈4–8 КиБ RSS на простаивающее.
- **Риск:** 32 КиБ — больше системных вызовов. На скоростях роутерного WAN (≤1 Гбит/с) незаметно [гипотеза]; на 10G-бенчмарках −10–20 %.
- **Forkop X:** VLESS+REALITY (основной тип узлов) использует этот путь. Предварительно Forkop может выставить `TACHYON_RELAY_BUF` в procd по объёму RAM.

### MEM-12. splice-pipe 1 МиБ на направление — kernel-память вне RSS — P2

- **Статус:**
  - [статически] `inbound/relay.rs:26,29,50`: `CHUNK` = `PIPE_START` = 1 МиБ, `F_SETPIPE_SZ`;
  - [подтверждено] 6 fd на соединение и kernel ≈10 КиБ на соединение при не-root;
  - медленный потребитель: 7,1 МиБ sock-памяти на соединение, в основном автонастройка TCP. Долю pipe отдельно не выделить.
- **Причина:** размер выбран под 51 Гбит/с на loopback.
- **Последствия:** от root (OpenWrt) лимиты `pipe-user-pages-*` не действуют. При быстрой WAN и медленном Wi-Fi-клиенте до 1 МиБ на направление лежит в pipe сверх сокетных буферов. 30 таких загрузок — до 30–60 МиБ kernel-памяти [гипотеза].
- **Исправление:**
  - `PIPE_START` 64 КиБ и рост до 256 КиБ–1 МиБ, только пока pipe опустошается быстро;
  - либо потолок по MemTotal.
- **Выигрыш:** до 0,75–0,94 МиБ kernel на занятое направление.
- **Риск:** по замеру в комментарии к коду 256 КиБ дают 15–21 Гбит/с на одном потоке, для роутера это с запасом.
- **Forkop X:** весь direct/bypass-трафик tproxy идёт через splice.

### MEM-13. Нет TCP keepalive на принятых сокетах и idle-тайм-аута relay — P2

- **Статус:**
  - [статически] `outbound/dial.rs:537-541`: при пустых `DialOptions` используется `TcpStream::connect` без `SO_KEEPALIVE`. Keepalive ставится только на пути `dial_tcp` (`:308-320`).
  - Принятые inbound-сокеты keepalive не получают.
  - [не проверено] Forkop задаёт `route.default_mark`; вероятно, это делает `DialOptions` непустыми, и тогда outbound keepalive есть.
- **Последствия:** соединения от исчезнувших LAN-клиентов (выключенный телефон) висят бесконечно: tracker, fd, буферы. Медленный рост за дни.
- **Исправление:** `SO_KEEPALIVE` (15 с / 15 с) на accepted-сокетах и всегда на outbound; опционально `TCP_USER_TIMEOUT`.
- **Выигрыш:** устраняет накопление (≈11–470 КиБ на зависшее соединение в зависимости от цепочки).
- **Риск:** нет.
- **Forkop X:** tproxy-соединения LAN-клиентов.

### MEM-14. DNS UDP: буфер 65 535 Б на каждый запрос в полёте — P3

- **Статус:** [статически] `dns/transport.rs:1181`.
- **Последствия:** всплеск в 100 запросов в полёте даёт ≈6,4 МиБ, кратковременно.
- **Исправление:** буфер 4 КиБ (EDNS 1232–4096) с fallback на TCP при TC.
- **Выигрыш:** ≈60 КиБ на запрос в полёте.
- **Риск:** нет.

### MEM-15. DNS LRU не меньше 1024 записей; FakeIP 16384 записей на семейство — P3

- **Статус:** [подтверждено]
  - +6,6 МиБ на 20 тыс. fakeip-имён (≈330 Б на запись), дальше рост упирается в потолок;
  - LRU 1024: случайные 50 тыс. имён дали +0,5 МиБ;
  - [статически] `dns/mod.rs:257-258` (`.max(1024)`), `dns/transport.rs:253`.
- **Последствия:**
  - ограничено, ≈5–11 МиБ в худшем случае (×2 с `store_fakeip` в cache.db, см. MEM-08);
  - `cache_capacity` нельзя опустить ниже 1024.
- **Исправление:** допустить меньшие значения; ёмкость FakeIP связать с настройкой или с MemTotal.
- **Выигрыш:** 2–5 МиБ на 128 МБ.
- **Риск:** чаще вытесняются fakeip-маппинги (повторные запросы).

### MEM-16. allocstat непригоден для целевых musl-сборок — P3

- **Статус:**
  - [статически] `core-cli/src/allocstat.rs:85-101` оборачивает `mimalloc::MiMalloc`, а зависимость `mimalloc` есть только для `target_arch = "x86_64"`. Значит, `--features allocstat` для aarch64 не соберётся [не собиралось].
  - Путь `/tmp/tachyon-allocstat.txt` фиксирован (`:169`).
- **Исправление:** оборачивать `std::alloc::System` вне x86_64; путь брать из `TACHYON_ALLOCSTAT`. Ровно это сделано в копии для аудита.
- **Выигрыш:** честные замеры кучи на роутере.
- **Риск:** нет.

### MEM-17. Слабый рост RSS при длительном обороте (musl) и удержание после спада — P2

- **Статус:** [подтверждено] §2.5.
  - anon на плато растёт ≈1,4 МиБ/мин при стабильном числе fd.
  - После спада 57 МиБ против 34 на старте: из них +10 МиБ живой кучи (DNS/FakeIP/cache), ≈13 МиБ удерживает аллокатор.
  - [гипотеза] Причина — memset переиспользованных 64 КиБ UDP-буферов и фрагментация mallocng.
- **Исправление:** в основном снимается исправлением MEM-02. Затем повторить тест на 1–2 часа на целевом aarch64.
- **Выигрыш:** 10–20 МиБ.
- **Риск:** нет.

### MEM-18. Прочее по статическому анализу — P2/P3, не измерялось

- **Shadowsocks:** `up_buf`/`down_buf` ≈128 КиБ каждый держатся всё время соединения (`inbound/mod.rs:603-662`), плюс `outbound/shadowsocks/stream.rs:12,20,272` — `rbuf` 256 КиБ без сжатия. ≈0,5–0,65 МиБ на соединение даже в простое. **P1 для пользователей SS.** Исправление — освобождать буферы после опустошения, как `PooledBuffer`.
- **TUN:** `inbound/tun.rs:50,1004-1011` — smoltcp 2×64 КиБ на сессию заранее; `poll_write` копирует весь буфер вызывающего (до 128 КиБ на элемент при очереди в 64 элемента). Forkop использует tproxy, поэтому **P3**.
- **QUIC:** hysteria2 — окна 8/20 МиБ; TUIC — дефолтные окна quinn (приём на соединение не ограничен, `outbound/quic.rs:223-252`). **P2.**
- **Clash `/connections`:** снимок строится через `serde_json::Value` на каждом тике. При 1000 соединений тело 329 КБ, временно ≈1–3 МиБ на тик [гипотеза]. Регистрация в трекере стоит ≈1–1,5 КиБ на соединение даже при выключенном Clash API. **P3.**
- **unbounded-каналы:** вне тестов только `outbound/dial.rs:705` (≤2 сообщения). Остальные каналы ограничены: логи 512 (`logging.rs:80`), TUN/anytls/XHTTP inbound 64. **Проблем нет.**
- **Расхождения в документации:** окна h2 «4/16 MiB» в README против 8/32 в коде; сводка BENCHMARK «6,5–15 MiB на TLS/gRPC» противоречит строкам в той же таблице. **P3.**

## 7. Ограничения аудита

- Замеры сделаны на x86_64. aarch64/musl не запускался: нет qemu-user и железа. musl-x86_64 — лучший доступный прокси для оценки аллокатора. Размер страниц, crypto, кэши и `available_parallelism` на роутере другие.
- Процесс не root:
  - размеры pipe ограничены `pipe-user-pages-soft`, общим для uid;
  - tproxy заменён на mixed;
  - TUN не проверялся.
- REALITY не измерялся: нужен handshake-target. Его стоимость оценена по VLESS+TLS: uTLS-путь [статически] даёт сопоставимые буферы.
- Hot reload, удалённое обновление rule set по `update_interval` и delta-обновление не измерялись.
- Нагрузку генерирует однопоточный Python: пропускная способность ниже реальной, и часть UDP-ответов теряется на стороне клиента.
- Синтетические SRS сжимаются хуже реальных. По числу записей `big-domains` сопоставим с HaGeZi Pro, по размеру файла нет.
- Внешних сетевых тестов не было: ничего не скачивалось, URLTest, probe и rule set шли только на loopback.
